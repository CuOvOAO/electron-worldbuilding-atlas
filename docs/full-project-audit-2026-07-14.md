# 手稿星图全项目复合审计报告

审计日期：2026-07-14  
审计基线：`main` / `0b76ad6 fix: use sqlite snapshot for integrity check`  
审计性质：只读代码、依赖、构建与发布链复核；未打开、创建或修改任何用户存档。

## 1. 结论摘要

1. 项目已经脱离 README 所描述的 V0 静态原型阶段：本地存档、核心资料 CRUD、关系网、地图、素材、回收站、Markdown/PNG 导出、完整备份 ZIP、恢复为新存档和完整性检查均有真实实现。
2. 当前代码可以通过 TypeScript 检查、生产构建和 Windows 目录打包，具备继续迭代的工程基础。
3. 当前不建议直接作为“资料安全已完成”的正式版本发布。本次确认 4 项 P0、13 项 P1 和 9 项 P2。
4. 最严重的资料风险是：应用关闭不会拦截未保存草稿；普通打开流程不拒绝高于当前代码版本的数据库；备份/恢复未执行完整数据库一致性验证；覆盖已有备份时先删除旧文件再重命名新文件。
5. 多个页面的“一次保存”由多个独立 IPC 写入组成，缺少一个主进程事务，失败时可能形成部分保存。
6. 素材删除没有统计或清理地图底图引用，会把正常用户操作变成完整性严重问题，并阻止后续完整备份。
7. Electron 安全边界不完整：没有 CSP、导航限制、IPC sender 校验或已打开存档白名单，且高权限 IPC 普遍接受渲染端传入的任意绝对路径。
8. 2026-07-14 的 `npm audit` 返回 3 个依赖漏洞：2 个 high、1 个 low；直接依赖 Electron 37.10.3 位于多个已知漏洞影响范围内。
9. 仓库没有正式测试脚本、测试框架或项目级 CI；V11 的验证成果没有沉淀成可重复回归测试。
10. 功能层面最明显的缺口是自动备份、手稿文件导入、HTML/PDF 导出、完整的素材/关系回收机制、存档管理和真实设置持久化。

## 3. 风险分级

- **P0**：可直接导致用户资料丢失、覆盖、错误升级，或在真正需要恢复时得到不可用存档。
- **P1**：高概率造成资料不一致、功能中断、安全边界突破、错误恢复结果或正式发布风险。
- **P2**：工程债、功能缺口、性能和可维护性问题，短期通常有绕行方式。

## 4. P0 阻断问题

### P0-01 普通打开流程允许旧应用写入更高版本数据库

- **触发条件**：用当前应用打开一个 `schema_migrations` 最高版本大于 7 的存档。
- **证据**：`src/main/vault/vaultService.ts:80-95` 在打开时直接调用 `runMigrations`；`src/main/db/migrations.ts:370-392` 只按“本地 migration 是否已应用”跳过或执行，不拒绝未知的更高版本。只有手动完整性检查和恢复检查比较最高支持版本。
- **影响**：未来版本数据库可被旧代码正常打开，随后旧版 CRUD 可能按过时字段和业务规则写入，造成不可逆兼容性破坏。
- **建议**：把“数据库版本不得高于当前代码支持版本”放入所有写入前的权威打开流程；检测后只允许拒绝打开或只读查看，不能继续迁移和写入。

### P0-02 备份和恢复没有验证 SQLite 内部完整性

- **触发条件**：`world.db` 存在局部页损坏、外键异常或未被当前查询触及的结构损坏。
- **证据**：`src/main/backup/backupService.ts:167-185` 只读取 migration 和已知素材引用；`src/main/backup/restoreService.ts:478-504` 只检查 migration 与部分核心表。两处均未执行 `PRAGMA integrity_check` / `quick_check` 和 `PRAGMA foreign_key_check`。
- **影响**：损坏数据库可能被成功标记为“完整备份”，恢复时又被接受并注册为新存档。ZIP 哈希只能证明文件与 manifest 一致，不能证明数据库可用。
- **建议**：备份应基于一致性快照校验后再打包；恢复应在 staging 中执行数据库完整性、外键、完整 schema 和关键逻辑引用校验，失败时不得注册或打开。

### P0-03 关闭应用不会保护未保存编辑

- **触发条件**：任何页面处于编辑模式且有未保存草稿时，用户关闭窗口、退出应用、系统关机或渲染进程刷新/崩溃。
- **证据**：`src/renderer/src/components/UnsavedChangesGuard.tsx:21-33` 只拦截应用内部导航；`src/main/index.ts:11-31,52-56` 没有窗口关闭握手；项目中不存在 `beforeunload`、`will-prevent-unload` 或主进程 close guard。
- **影响**：用户可在没有任何提示的情况下丢失本轮编辑草稿，违反项目已建立的“草稿后统一保存”模型。
- **建议**：建立主进程与 renderer 的关闭握手，覆盖窗口关闭、应用退出、更新/重启和系统关机；保存进行中也要阻止重复退出。

### P0-04 覆盖已有备份不是原子替换

- **触发条件**：用户选择覆盖已有备份，新 ZIP 已生成，但删除旧备份后 `renameSync` 因权限、杀毒软件占用、磁盘或文件系统异常失败。
- **证据**：`src/main/backup/backupService.ts:107-115` 先写 `.partial`，随后 `rmSync(finalPath)` 删除旧文件，再重命名新文件。
- **影响**：原有备份已经消失，新备份也可能未就位；若这是唯一可用备份，会直接降低恢复能力。
- **建议**：保留旧文件直到新 ZIP 完成二次读取校验；使用平台安全的替换策略和回滚文件，只有最终替换成功后才清理旧版本。

## 5. P1 高优先级问题

### P1-01 多模块“总保存”不是原子事务

- **证据**：词条保存依次更新主体、别名、正文块和关联（`CodexPage.tsx:113-126`）；事件主体与关联分开（`EventPage.tsx:132-151`）；时间线主体与事件排序分开（`TimelinePage.tsx:152-167`）；地图依次保存地图、图层、对象、再删除图层（`LocationMapView.tsx:595-630`）。
- **影响**：任一步失败都可能留下部分写入。UI 仍显示“未保存”，但数据库已被部分改变；取消编辑也只能恢复内存草稿，不能回滚已写数据库。
- **建议**：把每个页面的一次业务保存合并为单个主进程命令和单个 SQLite 事务，并返回完整的新状态。

### P1-02 删除素材会破坏地图底图引用

- **证据**：`src/main/ipc/assetIpc.ts:92-99` 仅清空角色头像和立绘；`listImageAssets` 的 `used_count` 也只统计角色（`153-164`），没有统计 `maps.background_asset_id`。
- **影响**：仍被地图使用的底图会被显示为“未使用”；删除后地图仍保留指向已删除素材的 ID。完整性检查把它列为 critical，完整备份校验也会拒绝继续。
- **建议**：统一素材引用注册表/查询；删除前统计角色与地图全部引用，并要求先解绑或在同一事务中安全处理。

### P1-03 Electron 高权限 IPC 缺少信任边界

- **证据**：`preload.ts` 暴露所有数据、备份、恢复、导出和素材命令；这些命令普遍接受 renderer 提供的 `vaultPath`。主进程没有 IPC sender URL 校验、当前存档 capability/白名单、导航限制或 `setWindowOpenHandler`。`src/renderer/index.html` 没有 CSP。
- **影响**：当前代码未发现 `dangerouslySetInnerHTML` 或直接外链，因此没有确认的现成 XSS 利用链；但一旦未来出现渲染脚本注入或意外导航，攻击面可扩大为任意目录数据库打开/迁移、文件复制、ZIP 解压和导出写文件。
- **建议**：主进程持有当前 vault token，不再信任任意路径；校验 sender；限制导航和新窗口；加入严格 CSP；把 preload API 缩减为明确参数类型。

### P1-04 Electron 运行时存在已知高危漏洞

- **现状**：安装版本为 Electron 37.10.3。
- **审计结果**：`npm audit` 将 Electron 标记为 high，列出多个 use-after-free、权限/来源判断和命令行注入相关公告；建议修复版本为 Electron 43.1.0，属于 semver major。
- **影响**：并非每条公告都能被当前功能触发，但 Electron 是正式包运行时，不能按普通开发依赖忽略。
- **建议**：建立独立升级分支，先升级到仍受支持且覆盖公告修复的 Electron，再完整验证 `node:sqlite`、electron-vite、electron-builder、备份恢复和 Windows 打包。禁止直接使用 `npm audit fix --force` 替代兼容验证。

### P1-05 完整性检查覆盖范围小于真实 schema

- **证据**：`integrityService.ts:75-86` 的核心表不包含 `codex_aliases`、`relationships`、`relationship_stages`、`map_layers`、`map_objects`、`content_blocks`、`entity_links`、`search_index`；项目 JSON 检查也未覆盖 `description`、`appVersion`，而正常打开要求这两个字段。
- **影响**：缺失真实业务表、列或逻辑引用的存档可能得到“正常”报告；用户随后打开具体功能才遇到失败。
- **建议**：以 migration 定义为权威生成完整表/列契约，并检查多态关联、软删除引用、地图图层/对象、时间线分支、关系阶段和所有素材引用。

### P1-06 外键异常只被降为 warning

- **证据**：`integrityService.ts:261-277` 对 `PRAGMA foreign_key_check` 返回异常只添加 warning。
- **影响**：报告仍允许“需要注意”而非“严重问题”，但外键断裂会导致读取丢项、保存失败或永久删除级联逻辑失真。
- **建议**：活动业务数据的外键异常应为 critical；只有明确可忽略的历史/软删除场景才能降级，并需要逐条分类。

### P1-07 版本号来源分裂

- **证据**：`package.json` 与 `preload.ts:4` 为 `0.0.1`；`vaultService.ts:27` 新建存档写 `0.1.0`；备份与恢复使用 `app.getVersion()`，因此恢复后的 `project.json` 又写成 `0.0.1`。
- **影响**：同一构建创建和恢复的存档显示不同 appVersion，manifest、设置页和未来兼容判断不可信。
- **建议**：只保留一个构建时版本源；存档格式版本、schema 版本和应用版本分别记录，禁止互相代替。

### P1-08 没有正式自动化测试和 CI

- **证据**：仓库无 `test` / `lint` 脚本、无测试目录、无项目级 CI 配置。当前 V11 的成功/失败、WAL 快照、ZIP 路径穿越等验证没有成为可重复测试。
- **影响**：备份、恢复、migration、回收站和地图这类高风险代码无法在后续修改时自动回归。
- **建议**：优先沉淀服务层测试，再补 IPC 契约和少量关键 Electron 流程测试；CI 至少执行类型检查、构建、测试、依赖审计和 `git diff --check`。

### P1-09 同一存档可被多个应用实例同时编辑

- **证据**：`src/main/index.ts` 未调用 `app.requestSingleInstanceLock()`；存档也没有进程锁、编辑会话 ID 或乐观并发版本字段。SQLite 未设置 `busy_timeout`。
- **影响**：两个窗口/实例可基于各自旧状态覆盖同一实体；备份 checkpoint 也可能频繁遇到 busy。
- **建议**：至少启用单实例；进一步对每个 vault 建立锁文件或只读退化，并为保存增加版本冲突检测。

### P1-10 备份/恢复对大文件采用整文件读入内存

- **证据**：备份和恢复的 `sha256File` 都使用 `readFileSync`；恢复允许最高 4 GB 解压总量。PNG/crop IPC 同样接受无明确大小上限的 base64。
- **影响**：大素材或构造的备份可让主进程长时间阻塞或内存耗尽；恢复前也没有可用磁盘空间预检、进度和取消。
- **建议**：哈希改为流式；设置单文件、图片像素、base64、总文件数和总大小限制；解压前预检空间；长任务提供进度和取消。

### P1-11 备份写完后没有重新打开自检

- **证据**：`backupService.ts:107-116` 只检查 `.partial` 文件大小大于 0，然后重命名并返回成功。
- **影响**：ZIP 中央目录写入、磁盘落盘或最终文件损坏不能在导出时被发现，问题会延迟到真正恢复时出现。
- **建议**：最终成功前重新读取 ZIP，验证 manifest、条目数量、大小和哈希；必要时执行一次与恢复服务共用的只读检查。

### P1-12 `dataIpc.ts` 存在持久化乱码字符串

- **证据**：例如 `dataIpc.ts:255,297,407,601,2407,2473` 的“未命名”默认值已经是 mojibake；`1669-1676` 的搜索省略号也为乱码。
- **影响**：用户留空名称时，乱码会被直接写入数据库；全局搜索摘要会显示乱码。大量错误日志和错误文案也失去可读性。
- **建议**：单独进行编码修复并加测试，区分只影响日志的字符串与会写入数据库/显示给用户的字符串。

### P1-13 发布包包含不必要的构建工具

- **证据**：`vite`、`electron-vite`、`@vitejs/plugin-react` 和多个 `@types/*` 被放在 `dependencies`；打包产物的 `app.asar.unpacked` 实际包含 Vite、Rollup 和 esbuild 可执行文件。
- **影响**：正式包体、攻击面和漏洞扫描噪声增加；npm audit 的 esbuild low 漏洞也进入发布包内容。
- **建议**：把纯构建与类型包移到 `devDependencies`，确认主进程只保留真正运行时需要的 `archiver`、`yauzl` 等依赖，再检查打包文件清单。

## 6. P2 工程与体验问题

1. `project.json.updatedAt` 不随资料编辑更新；存档选择页的“最后编辑”长期停留在创建/恢复时间。
2. `recent-vaults.json` 直接覆盖写入，不是临时文件加原子替换；损坏时整个最近列表被静默当作空列表。
3. `README.md` 仍宣称所有数据来自 mock、数据库和导出未实现，与当前真实项目严重不符。
4. `src/main/database.ts` 仍保留“SQLite intentionally deferred”的 V0 占位，已经失真。
5. `dataIpc.ts` 约 2514 行、`LocationMapView.tsx` 约 3058 行；职责过度集中，增加事务边界和回归测试难度。
6. renderer 生产 JS 约 1.38 MB，四张纸张纹理合计约 7.6 MB；当前没有代码分割和资源体积预算。
7. Windows 发布配置缺少应用图标、author、明确签名证书/发布通道和升级策略。
8. 仓库包含 `.codex-tmp-docx/handoff.zip`（约 25.65 MB）、大量 V10 raw/qc/preview 生成物；Git pack 约 145.66 MB，仓库卫生和克隆成本偏高。
9. 多个 update/delete IPC 不检查 SQLite `changes`，目标已不存在时仍可能返回成功对象，造成“看似保存成功、实际未写入”的假成功。

## 8. 安全边界评价

### 已做对的部分

- BrowserWindow 已启用 `contextIsolation`，并关闭 `nodeIntegration`。
- renderer 未发现 `dangerouslySetInnerHTML`、`eval` 或直接外部网络请求。
- 素材路径限制在 vault 的 `assets` 下。
- 恢复 ZIP 已防止绝对路径、`..`、反斜杠、重复条目、符号链接和超量条目，Zip Slip 防护整体较扎实。
- 恢复使用 staging 目录，最终通过 rename 注册为新存档，正常路径不会覆盖既有存档。
- V11-C.1 对活跃 WAL 数据库采用 Online Backup API 临时快照，避免直接对 live DB 使用 `immutable=1`。

### 尚未形成的防线

- renderer 到主进程之间仍是“路径即权限”，缺少 capability 和 sender 校验。
- 没有 CSP、导航白名单、权限请求拒绝策略和外部链接统一处理。
- IPC 参数大量使用 `unknown` / `any`，主进程仅做局部字段验证，没有统一 schema 和大小限制。
- 备份是完整明文资料包，没有加密或敏感信息提示。对于本地优先产品这不是默认缺陷，但正式文档必须明确“拿到 ZIP 即拿到全部世界观资料”。
